# IEC 62443 (OT/industrial, 7 foundational requirements)

**Status: Full**
**Source**: [issue #160](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/160)
**Reference**: IEC 62443 — reference standard for industrial/OT network cybersecurity, structured around 7 "Foundational Requirements" (FR1–FR7), each rated across 4 security levels (SL-1 to SL-4), plus a **zones and conduits** segmentation model (grouping assets by shared risk level, inter-zone communication via controlled conduits).
**Last verified**: 2026-09-29

## Scope note

Second of four frameworks added after the initial series closed. TBP explicitly claims the **I-INTEGRITY** invariant — "air-gapping of industrial control systems" — this is the sector-standard reference for exactly that use case, absent from the original list despite the direct match.

Legend: ✅ Covered/strong technical evidence · 🟡 Partial · 🔴 Real gap · ⚪ Out of TBP's scope

## The 7 foundational requirements vs. TBP

| FR | Requirement | Status | Detail |
|---|---|---|---|
| **FR1** | Identification and authentication control | ✅ | `AgentRegistry` (#125) + mTLS (#124)/`SO_PEERCRED` — identity resolved by the broker, never self-declared. |
| **FR2** | Use control (authorization, least privilege) | ✅ | OPA default-deny + registry-capped class/quota — exactly what "use control" asks for. |
| **FR3** | System integrity (protection against unauthorized modification) | ✅ | Tamper-proof Merkle chain (tessera), measured boot (T31, §6.3), signed and revision-checked OPA bundle (§106/§92.A5). |
| **FR4** | Data confidentiality | ✅ | Hash-only doctrine (§6.2), encryption in transit (mTLS). |
| **FR5** | Restricted data flows (segmentation) | ✅ | **Direct match with the zones/conduits model** — see below. |
| **FR6** | Timely response to events | ⚪ posture | Same recurring gap as CSF Respond ([#153](153-nist-csf-800-53.md)) and GDPR breach notification ([#155](155-gdpr.md)): `OnTrip`/the T14 alarm triggers, but there's no formal incident-response process or notification timeline. **To close:** as CSF Respond ([#153](153-nist-csf-800-53.md)): alerting on the alarm output plus a written playbook with a notification timeline. |
| **FR7** | Resource availability | ⚪ deliberate tradeoff | Same nuance as SOC 2 Availability ([#154](154-soc2.md)): generalized fail-closed DELIBERATELY prioritizes safety over availability. **To close:** as SOC 2 Availability ([#154](154-soc2.md)): document the tradeoff and run redundant cells. |

## Zones and conduits — this catalog's best argument

Beyond FR5 alone, IEC 62443's zones/conduits model is a near-exact description of TBP's multi-cell architecture: each cell (dedicated VM, §7.1) is a homogeneous-trust zone; inter-cell fencing (T29, epoch authority, quarantine §7.3) prevents a compromised zone from affecting others; separate data/admin sockets and VLAN segmentation are explicitly controlled conduits rather than a flat network. This is an architecture that could have been designed by reading IEC 62443, while in fact it was developed independently.

## Summary

**Second-best score in the series**, after [Zero Trust (#159)](159-nist-800-207-zero-trust.md) — expected, both frameworks share the same philosophy of strict segmentation and systematic authentication.

**Same posture gap seen elsewhere** (FR6): TBP supplies the trigger, never the response process — third confirmation of this exact pattern, after NIST CSF Respond ([#153](153-nist-csf-800-53.md)) and GDPR Art. 33/34 ([#155](155-gdpr.md)).

**Concrete recommendation**: the zones/conduits model would give an excellent vocabulary for formally documenting TBP's multi-cell architecture in a future `Architecture.md`/`deploy/` doc — a "cell = zone, admin/data socket = conduit" diagram would be immediately legible to an industrial-sector auditor.
