# FIPS 140-3 (cryptographic module validation)

**Status: Full** (documentary clarification only — see scope note; TBP cannot itself be "FIPS validated")
**Source**: [issue #161](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/161)
**Reference**: FIPS 140-3 — NIST standard for validating cryptographic MODULES (hardware/firmware/software), 4 increasing security levels, certified through the CMVP program.
**Last verified**: 2026-09-28

## Scope note — read this before the table

**FIPS 140-3 certifies a PRODUCT (a specific cryptographic module, with a CMVP certificate number), never an application that uses one.** TBP can therefore never itself be "FIPS 140-3 validated" — that's as structurally impossible as a web application being "Intel certified." What IS verifiable: (a) does TBP use FIPS-approved algorithms? (b) does TBP's PKCS#11 abstraction allow plugging in an actually-certified module? (c) does TBP itself verify the properties a module of a given level should guarantee?

Legend: ✅ Covered/strong technical evidence · 🟡 Partial · ⚪ Out of TBP's scope (property of the HSM product chosen at deployment, not of TBP's code)

## The 4 levels vs. TBP

| Level | Requirement | Status | Detail |
|---|---|---|---|
| **Level 1** | At least one approved algorithm/security function, no physical requirement | ✅ | TBP uses exclusively approved algorithms: **Ed25519/EdDSA has been approved since FIPS 186-5** (2023, replacing 186-4) for all signatures (operators, quorum, contract plans, dev tokens); SHA-256 for leaf hashing; RSA for OPA bundle signing (§106). Satisfied by the project's algorithm choices alone, independent of which module executes them. |
| **Level 2** | Tamper-evidence (coatings/seals) | ⚪ | Physical property of the HSM product chosen at deployment (YubiHSM2, AWS CloudHSM, Azure Key Vault…) — outside TBP's code by construction. |
| **Level 3** | Physical tamper resistance, identity-based authentication, physical/logical separation of "critical security parameters" | 🟡 | **The most interesting point in this catalog**: TBP cannot GUARANTEE this property (it belongs to the module), but it VERIFIES and ENFORCES it at startup — security review #114 explicitly checks `CKA_SENSITIVE=true` AND `CKA_EXTRACTABLE=false` on the loaded PKCS#11 key, and refuses to start otherwise. TBP acts as a Level-3 compliance GUARDRAIL, without being the certified module itself. |
| **Level 4** | Enhanced robustness against environmental attacks | ⚪ | Physical property of the HSM hardware — out of reach by construction. |

## The distinction never to blur in documentation

`DevSigner` (an Ed25519 seed in a 0600 file, dev/lab only) has NO FIPS claim whatsoever — explicitly outside cryptographic-module territory, and already gated by the devmode-sentinel doctrine (#113: an independent second signal required to use it). Any FIPS compliance documentation for TBP must be scoped EXCLUSIVELY to the `PKCS11Signer` path, never the dev path.

## Summary

**Verifiable and correct claim to document**: "TBP uses exclusively FIPS-approved cryptographic algorithms (EdDSA/FIPS 186-5, SHA-256, RSA) and actively verifies at startup that the loaded signing key satisfies the non-extractability properties of a FIPS 140-3 Level 3 module" — true, precise, and distinct from "TBP is FIPS 140-3 validated" (false and structurally impossible to claim).

**Documentation recommendation**: list commonly FIPS 140-3-certified PKCS#11 HSM products (AWS CloudHSM, Azure Key Vault, YubiHSM2) in `deploy/cellule.md` or a future compliance doc as recommended deployment choices for regulated environments — TBP provides the interface and the verification, the deployment chooses the certified module.

**No code gap identified here** — a rare case in this series: the only action is documentary (clarifying what "FIPS" means for TBP), not a technical fix. This file *is* that documentation.
