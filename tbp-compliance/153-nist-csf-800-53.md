**Status: Partial**
**Source**: [issue #153](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/153) · related fix: [issue #165 / PR #166](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/165) (SkillRegistry, IDENTIFY)

**Last verified**: 2026-09-29

## Scope note

SP 800-53 control families (AC — Access Control, IA — Identification & Authentication, SC — System & Communications Protection, AU — Audit & Accountability, CM — Configuration Management, etc.) cover almost the same ground as the Technological theme of ISO 27001/27002 already catalogued in [#152](152-iso-iec-27001-27002.md), with a near 1:1 mapping in official NIST/ISO literature — same statuses (✅ on AC/IA/SC/AU, 🟡 on CM, ⚪ on organizational families like PM/PS). This catalog instead focuses on what's new: CSF 2.0's own Govern→Identify→Protect→Detect→Respond→Recover cycle.

Legend: ✅ Covered/strong technical evidence · 🟡 Partial · 🔴 Real gap · ⚪ Out of TBP's scope

## The 6 CSF 2.0 functions vs. TBP

| Function | Content | Status | Detail |
|---|---|---|---|
| **GOVERN** | Strategy, risk context, roles, policy | ⚪ | Same conclusion as the RMF's Govern function ([#147](147-nist-ai-rmf.md)) — organizational process, not a software feature. |
| **IDENTIFY** | Asset inventory, risk assessment, supply-chain risk management | ✅ | `AgentRegistry`/genesis manifest/`cells.json` are a real out-of-band inventory — scoped to identities (agents/operators/cells), not a generalized asset inventory. **The supply-chain-risk sub-point is closed** by `SkillRegistry` (#165, PR #166) — the seventh and final confirmation across this series. |
| **PROTECT** | Access control, data security, platform hardening, infrastructure resilience | ✅ | Where the bulk of TBP's controls live — same finding as ISO 27001's Technological theme ([#152](152-iso-iec-27001-27002.md)): OPA/`AgentRegistry`/`QuorumGate` (access), hash-only leaves (data), HSM/mTLS/fail-closed (hardening). |
| **DETECT** | Continuous monitoring, abnormal-event analysis | 🔴 | The audit chain and `BrokerStats` supply the monitoring DATA; no active anomaly detection built on top (same gap as AST08 "poor scanning," [#142](142-owasp-agentic-skills-top10.md)). Tracked by [#181](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/181) (behavioural profile by sequence). |
| **RESPOND** | Incident handling, analysis, mitigation, reporting | ⚪ posture | `OnTrip`/the T14 alarm is a real TRIGGER — but TBP has no incident-response PROCESS (playbooks, formal reporting). This is a deliberate posture, not an oversight: TBP provides the alarm signal, never the response procedure, consistent with being an enforcement point rather than an incident-governance platform. Documented here rather than "fixed." **To close:** wire the daemons' alarm output and the audit chain into your alerting, and write the playbook (who acts on a `refused` posture, who gathers the quorum to reconfirm). |
| **RECOVER** | Execute recovery plan, continuous improvement, communication | ✅ · ⚪ backups | An underrated but real point: doctrine §93 (pepd restart → `refused` posture, never a silent `monitor`, until quorum reconfirms) *is* a controlled, verified recovery procedure — one of this catalog's best answers, as long as it's not confused with data backup/restore (out of scope, see [#152](152-iso-iec-27001-27002.md)). **To close (data):** backups as in [#152](152-iso-iec-27001-27002.md). |

## Summary

**New strong point identified here**: the RECOVER function finds a concrete, already-existing answer in doctrine §93 (quorum-reconfirmed restart) — a good example of a control that turns out "accidentally" compliant with a framework it wasn't written with in mind.

**Closed since the original catalog**: IDENTIFY's supply-chain-risk sub-point, by `SkillRegistry` (#165, PR #166) — the seventh and final independent framework in this series to confirm the same gap.

**DETECT remains the constant weak point** across the whole series (AST08, LLM/MAESTRO implicitly, here): TBP produces exploitable monitoring data but never performs active anomalous-behavior detection itself — consistent with its assumed enforcement posture, not a detector (see the Defense Evasion nuance in [MITRE ATLAS #145](145-mitre-atlas.md)).

**RESPOND is a deliberate posture, not a defect**: documented explicitly rather than turned into a code fix — TBP supplies the signal, not the incident-response procedure. The same pattern recurs in [GDPR Art. 33/34 (#155)](155-gdpr.md) and [IEC 62443 FR6 (#160)](160-iec-62443.md).
