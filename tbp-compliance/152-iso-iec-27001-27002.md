## Organizational (37), People (8), Physical (14)

Security policies, roles, personnel screening, training, premises security, secure disposal, clean-desk, etc. — **overwhelmingly ⚪ out of TBP's scope**: HR processes, documentary policies, and physical premises security, none implementable in software. One notable exception: **supplier-relationship controls** (managing security in third-party agreements), closed by `SkillRegistry` (#165, PR #166) — see below.

## Technological (34 controls) — by functional group

| Functional group | Status | Detail |
|---|---|---|
| Access control / privileged access management | ✅ | `AgentRegistry` (#125) + OPA evaluation + `QuorumGate` — the core of TBP's access control lives in this chain. |
| Identification and authentication | ✅ | Mandatory mTLS for network access (#124), `SO_PEERCRED` for the Unix socket, HSM identity for the issuer. No human MFA — not relevant, TBP has no user login surface. |
| Cryptography, key management | ✅ | Non-extractable HSM/PKCS#11 signer (review #114), Ed25519 signatures everywhere (operators, plans, tokens), RSA-signed OPA bundle (§106). |
| Logging and monitoring | ✅ | tessera audit chain, master-chain anchoring, `src/supervision` (T34) — one of the most mature layers in this repo. |
| Network security | ✅ | mTLS (#124), 0660 Unix-socket permissions, VLAN/802.1X-EAP-TLS NAC documented (`deploy/router-debian.md`). |
| Secure development lifecycle, secure coding | ✅ | Demonstrated by this repo's own practice: fail-closed doctrine, non-vacuous test discipline (every fix proven by reproducing the failure then the fix), CI (`selftest.yml`). |
| Configuration management | ✅ | The devmode-sentinel doctrine (#113) protects dev escape hatches, and the dev flags actually active at a start are recorded as a log leaf (`devmode.RecordActive`, [#208](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/208)) so a cell that ran with one is visible after the fact; measured boot (T31) attests the policy bundle, OPA config, `brokerd` binary and AI container; and, since [#192](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/192), the files that carry the cell's trust are measured by the daemon that loads them (`registry.ProvisioningGuard`): `brokerd` — operator keys, agent registry, genesis manifest, skill registry, mTLS client CA; `pepd` — issuer and quorum keyrings; both accept extra files, and both attest the scale settings (`TBP_QUORUM_MIN`, topology — [#224](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/224)): lowering k by editing the environment is a divergence authorised only by the k that was attested. A changed file refuses to start and is named (never its content); a deliberate change needs a quorum proof (`quorumproof`, k = `TBP_QUORUM_MIN`: at scale 1 the administrator alone signs), verified against the controller keys *as attested in the witness*, never the edited file ([#218](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/218) — the first version checked it against the file an attacker could edit). **Limits:** a witness lost and re-engaged falls back to trust on first use for the controller keys; files are loaded once, so a change is caught at the next start, not while running; the witness is signed by the cell key, so an attacker holding that key and able to write the witness can forge it. **To close (deployment):** set `TBP_PROVISIONING_WITNESS_FILE` outside the registry directory on every daemon; adopting it on a cell that already ran takes one transition proof (see `deploy/cellule.md`). Tested end to end in `deploy/selftest`. |
| Data masking / leak prevention (DLP) | ✅ | The hash-only leaf doctrine (§6.2) *is* DLP by construction for the audit chain — nothing sensitive is ever written there to begin with. |
| Capacity management | ⚪ | `EnvelopeLedger` has fixed capacity (bounded map), no dynamic reallocation. **To close:** size capacity before deployment (scale guides, [#86](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/86)) and alert on saturation. |
| Malware protection, web filtering | ⚪ | Out of TBP's scope — overlaps the scanning gap already noted in AST08 ([#142](142-owasp-agentic-skills-top10.md)). |
| Backup | ⚪ | Outside the broker's own role (operational/deployment concern); the append-only chain with master-chain anchoring offers a form of tamper resilience, but is NOT backup/recovery — not to be conflated. **To close:** back up the registry directory (`TBP_REGISTRY_DIR`) and the provisioning files (agents, operators, skills, keyrings, policy bundle) on your normal schedule, keep one copy offline, and test a restore by re-verifying the chain. |

## Summary

**TBP is strong exactly where expected**: of the 34 technological controls, most functional groups are ✅ — consistent with TBP being a technical-security project, not a general-compliance one.

**Closed since the original catalog**: the supplier-relationship gap, by `SkillRegistry` (#165, PR #166) — the sixth independent framework (after [#142](142-owasp-agentic-skills-top10.md), [#143](143-owasp-llm-top10.md), [#144](144-csa-maestro.md), [#145](145-mitre-atlas.md), [#148](148-iso-iec-42001.md)) that pointed at this exact gap. No 🔴 remains in this catalog.

**Nuance not to lose**: audit-chain resilience (append-only, anchored) is not a backup — two distinct properties too often conflated in a quick compliance write-up.
