# SLSA v1.0 (build provenance levels)

**Status: Full**
**Source**: [issue #156](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/156) · fix: [issue #174 / PR #175](https://github.com/philippeabraxas-jpg/TBP-NETWORK/issues/174)
**Reference**: SLSA v1.0 (Supply-chain Levels for Software Artifacts) — 4 levels (L0–L3) of build-chain provenance guarantee for a software artifact.
**Last verified**: 2026-09-28

## Scope note

Earlier catalogs in this series ([#142](142-owasp-agentic-skills-top10.md)–[#155](155-gdpr.md)) evaluated the supply chain of SKILLS/TOOLS that TBP would authorize (the recurring `SkillRegistry` gap). SLSA asks a different, complementary question: does **TBP's own build** (`pepd`/`brokerd`/`supervisord` binaries, OPA policy bundles) have verifiable provenance? This catalog evaluates TBP as a PRODUCER of artifacts, not a consumer of third-party skills.

Legend: ✅ Covered · 🔴 Real gap (needs code; the row links the issue that tracks it) · ⚪ Not TBP's concern (the row says why and, for a deployment, how to close it). A combined status splits one control between what TBP covers and what stays with the deployer. See the [catalogue README](README.md).

## The levels vs. TBP's build

| Level | Requirement | Status | Detail |
|---|---|---|---|
| **L1** | Provenance exists (documented build platform and process), even unsigned | ✅ | `release.yml` builds `pepd`/`brokerd`/`supervisord` and produces an explicit in-toto provenance document via `slsa-framework/slsa-github-generator` (#174, PR #175). |
| **L2** | Hosted build + tamper-resistant digital signature | ✅ | The OPA policy bundle already reached this level (§106); the Go binaries now do too — hosted build (GitHub Actions) + OIDC-signed provenance (`id-token: write`, never a repo-held key) (#174, PR #175). |
| **L3** | Platform isolation, non-forgeable provenance, ephemeral build environments | ✅ | `release.yml`: a separate `provenance` job (`needs: [build]`), generated by `slsa-github-generator` (the official reusable generator, never reimplemented locally) in an Actions environment isolated from the `build` job, OIDC-signed — non-forgeable by construction. Verified end-to-end via a manual `workflow_dispatch` run on `main` (#174, PR #175). |

## Summary

**Most interesting observation**: TBP already applies SLSA's philosophy (pinned source, signed artifact, never dynamically resolved) to its OWN configuration data — `AgentRegistry`, `OperatorKeys`, the genesis manifest are all out-of-band, pinned tables with the same anti-dynamic-resolution doctrine SLSA asks of a build artifact. The OPA bundle (§106) already went further with real build+signature; the Go binaries now do too.

**Distinct from the other gaps in this series**: not a `SkillRegistry` duplicate — this is TBP's own build, not the skills TBP would authorize. First gap in the whole series that didn't overlap anything existing.

**Fixed**: `slsa-github-generator` is now wired into `release.yml` for `pepd`/`brokerd`/`supervisord`, reaching L3 (not just L2) — an isolated CI change, no broker code touched (#174, PR #175).
