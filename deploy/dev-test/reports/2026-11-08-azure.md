# First real run of the site test — Azure, 2026-11-08 (draft, partial)

_Version française : [2026-11-08-azure.fr.md](2026-11-08-azure.fr.md). Part of [deploy/dev-test](../README.md)._

> **A draft, not a complete report.** One run, by one person, on **Azure only**, on 8 November 2026. Steps 1 to 14 of
> [site.md](../site.md) were done, with two of the network attacks of "Attack it"; the file attacks on M2, a hard stop of
> `pepd` and a flood of invalid requests were done the next day (below), and so were the attacks on the files of M1 (the files the cell measures). The complete
> report will come once the test has been run on AWS as well. Nothing here is a performance claim:
> these are measures of one setup, taken by hand.

## What it found

| # | Finding | State |
|---|---|---|
| 1 | The machine that builds the cell needs a C compiler: without `gcc` the build fails with `undefined: pkcs11.Attribute` | fixed (the script says so before building; the guides list it) |
| 2 | A new Azure subscription can be refused some sizes and a whole region (*"not accepting new customers"*), which the template validation does not show | documented in the Azure guide, with a free test of the region |
| 3 | The live console drew nothing that arrived after the page was opened (`Requests (0)`), because the page read each update wrapped; a reload showed it | fixed; the browser test now posts a request after the page is open |
| 4 | A token lives 30 to 60 s; "the same token again" gave `stale-token` after three minutes. An approval from `m1 sign` gave `plan-deviation` the second time. A refused attempt does not use the approval up | the guide says so |
| 5 | An error message of `m2 mode` was in French in the middle of English output | the quorum messages of the mode path are in English |
| 6 | One `opa-timeout` in the first 67 decisions. The cell gives OPA a strict 5 ms budget (spec §9.1). OPA alone gave none in 4,000 requests of one flow, so this one looks like a rare tail event; its cause is **not established** | open; to count under load |
| 7 | The cell's decision takes about 550 ms with a spread of 3 ms over 60 requests; an accepted one about 780 ms (class I) and 1.04 s (class W). `pepd`, although in its default asynchronous write mode, takes about 260 ms for a valid token against about 7 ms for a refusal. The very narrow spread points to a fixed wait rather than computation | open; **not explained**: to measure by step inside `pepd` and the cell |
| 8 | **Parallel decisions of one agent are refused beyond two at a time by default**: 0 % at 1 and 2, 2 % at 3, 27 % at 4, 87 % at 16 (`opa-overloaded`, instantly). With 4 places: 0 % at 4. The cell's own settings explain the cap, not a fault of OPA; what holds a place, and for how long, is **not measured** | open; the knob is `TBP_OPA_MAX_INFLIGHT`; a limit to state in the release notes |
| 9 | **A `kill -9` right after a record is written to the journal leaves an orphan**: a record whose leaf is not in the log. 3 of 3 at delay 0 (one by accident, on a start-up event), 0 of 1 at 0.3 s. Nothing was executed. `tbp-audit verify` finds and names it (exit 1); a restart does not close it; there is no tool to close it | open; to describe in the release notes; the width of the window is not measured |
| 10 | **Each invalid, non-empty token costs a journal record and a leaf** (about 360 bytes together) and nothing limits it: 22,000 in a row, at 73 to 164 a second, left no alarm and no loss. The cut that "no leaf, no answer" implies was not reached, and a faster flood or a full disk were not tried | open; no quota yet |
| 11 | The rate of invalid requests **fell** from about 164/s (8 at once) to about 73/s (64 at once) | open; bottleneck not located |

## Complement of 9 November (same machines, same setup)

Same three machines, started again the next day; to our knowledge nothing was updated on them. Done by hand, from the commands of
[aws-test-plan.md](aws-test-plan.md), parts 6 to 8, run on Azure because the AWS account was still being verified.

**Files of M2** (`m2 down`, change one file, `m2 up`, restore). Every change was refused, and each refusal names its cause:

| Change | Result |
|---|---|
| `TBP_QUORUM_MIN=2` lowered to `1` | `pepd` does not start: `provisioning-divergence`, changed: `quorum-settings`; a transition would need a signed proof (`TBP_PROVISIONING_TRANSITION_PROOF_FILE`), not tried |
| a measured file (`ai-container.txt`) changed | `pepd` does not start: `manifest-boot-divergence` (§6.3) |
| one byte of the rule bundle corrupted | OPA does not start: `bundle read failed: flate: corrupt input`. This tests the archive, **not the signature**: the archive was unreadable before any signature check |
| a comment added to a rule file, archive repacked cleanly | OPA does not start: `file ./policies/rego/pack_skill_tier.rego not included in bundle signature` |
| a second, random key added to the issuer keyring | `pepd` does not start: `provisioning-divergence`, changed: `issuer-keyring` |

The `pepd` and `brokerd` messages are in French.

**Files of M1** (the cell), by a script that backed up the files, changed one, ran `m1 up` and restored. Eight changes to files that
the cell measures were refused, each with its cause; one change to a setting that is deliberately not measured started:

| Change | Result |
|---|---|
| an agent (`agent-evil`, class 3) added to the registry | `brokerd` does not start: `provisioning-divergence`, changed: `agent-registry` |
| `TBP_QUORUM_MIN` lowered to 1 | refused: `quorum-settings` |
| the operator who may only submit also given `approve` | refused: `operator-keys` |
| a controller's public key replaced | refused: `genesis-manifest` |
| the certificate authority of the agents replaced by the server's | refused: `tls-client-ca` |
| a comment added to a rule file, archive repacked | OPA does not start: `file ./policies/rego/pack_skill_tier.rego not included in bundle signature` |
| the key that verifies the rules replaced | OPA does not start: `failed to verify JWT signature: crypto/rsa: verification error` |
| the admission queue of OPA switched off (`TBP_OPA_MAX_INFLIGHT=0`) | refused: `security-posture` |
| the admission queue set to 4 (`TBP_OPA_MAX_INFLIGHT=4`) | **starts**, as designed: sizes and durations are outside the commitment (`src/pep/posture.go`) |

Every refusal says that a transition would need a signed proof (`TBP_PROVISIONING_TRANSITION_PROOF_FILE`), which was not tried.
**Not tried**: the files that the cell does not list among those it measures (the issuer seed, the TLS certificate and key of the
cell, the key of the audit journal, the settings outside the posture such as the translator). Whether changing them is noticed is not
known; it is the first thing to try next.

**A hard stop of `pepd`** (`kill -9`) at the moment a record is written to its journal. A script watched the encrypted journal
and killed `pepd` as soon as a new line appeared (after a delay of 0 or 0.3 s), then restarted `pepd` and ran `tbp-audit verify`
with the log:

| Try | Delay | What the agent got | Result of `tbp-audit verify` |
|---|---|---|---|
| 1 (posture not noted) | 0 | `[503] pepd gave no verdict: RemoteDisconnected` | one **orphan**: a verdict record (`kind=1`) whose leaf is not in the log |
| accident: a killer left armed killed `pepd` while it was starting | 0 | (no request) | a second orphan: a start-up event (`kind=11`) |
| A (posture `refused`) | 0 | `[503] pepd gave no verdict` | a third orphan, a verdict record |
| B (posture `refused`) | 0.3 s | `[403]`, verdict `allow: true`, `forwarded: false`, `leaf_written: true`, 264 ms | **no new orphan** |

What this shows: nothing was executed in any try (the application acts on `forwarded: true`, and `pepd` had given no verdict); the
three orphans are the only failures of `tbp-audit verify`, which exits 1 and names each one; a restart of `pepd` adds its own start-up
leaves and does not close them; no tool exists to re-insert or close an orphan. What it does not show: how wide the window is
between 0 and 0.3 s (one try per delay), or how often a crash not aimed at it would fall into it. The killer fires when the line
becomes visible in the file; whether that is before the end of the `fsync` is a guess. The link between the first orphan and the
request is by time only (the trace id says 17:11:02, the record 17:11:03.46).

**A flood of invalid requests** to the application of M2, with a non-empty token that is not a valid token (`AAAA`), from M3:

| | Flood 1 | Flood 2 | Flood 3 |
|---|---|---|---|
| Requests, at once | 2,000, 8 | 20,000, 64 | 6,000, 64 |
| Time | 12.2 s | 4 min 34 s | not timed |
| Rate | about 164/s | about 73/s | |
| Answers | 2,000 × `[403]` | 20,000 × `[403]` | 6,000 × `[403]` |

- **Each invalid request wrote one record** in the journal of M2 (91 → 2,091 → 22,093 lines, exactly) and one leaf in the log:
  after flood 2, `tbp-audit verify` examined 22,095 records, found 22,092 leaves and the same three failures as before, none new.
- Cost on disk: about 250 bytes of journal and about 110 bytes of registry per request (`audit` 32 K → 5.4 M, `registry` 316 K →
  2.5 M). Extrapolated, not measured over time: about 2.3 GB a day at 73 requests a second.
- No alarm of the durability path in the log of `pepd` (one `ALARME`, the restart's; counted after flood 2, not after flood 3), no refusal of a valid request.
- The rate **fell** when the parallelism went from 8 to 64. Where the bottleneck is (the application of the test, `pepd`, its
  journal) is not known.
- A valid request after the floods: `allow: true`, `leaf_written: true`, 289 ms (`elapsed_us`, measured inside `pepd`). A valid
  request **during** flood 3: the same, 217 ms, 1.36 s end to end. On 9 November the four valid verdicts took 217, 259, 264 and 289 ms
  (8 November: 255 to 272 ms): the narrow spread that finding 7 took for a fixed wait is wider than it looked.

## What this does not say

One person, one run, a few dozen requests per measure, one subject for the concurrency series, no load from several agents. The
550 ms, 780 ms and 260 ms are what this setup gave, not a property of Azure, and the points marked "not established", "not
measured" or "not explained" are not claims. The same run on AWS, then with several agents, is what the complete report is for.

The additions of 9 November are also by hand, one run each, one or two tries per delay for the hard stop, and a flood from a client
that may have been its own limit (`curl`): they say that the failures described exist, not how often they happen, nor where the
ceilings are.
